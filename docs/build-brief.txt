Enterprise E-Commerce Platform

Target stack: Next.js 16.3.8 + React 19.3 + TypeScript + NestJS 12 + Node.js 24 LTS + PostgreSQL + Redis. The system must run end-to-end with seeded dummy data and no paid service required for local development.

1. Stack decision and architecture
Use one language across the application wherever practical: TypeScript. The frontend is Next.js and React; the dedicated API is NestJS. This keeps the developer experience coherent while giving the backend enough structure to demonstrate serious application architecture.
Web application
Next.js 16.3.8 (App Router), React 19.3, TypeScript strict mode, Server Components by default, Client Components only for interaction-heavy UI.
Backend API
NestJS 12 on Node.js 24 LTS. REST-first API with OpenAPI/Swagger, WebSocket or SSE channels for selected realtime events, and modular domain boundaries.
Workspace
pnpm workspaces + Turborepo. Apps: web, api, worker. Packages: ui, database, contracts, config, eslint-config, tsconfig.
Primary database
PostgreSQL. Use an ORM with migrations, typed schema and transactions (Prisma ORM is preferred unless compatibility requires another mature TypeScript ORM).
Cache / rate limits
Redis. Use it for cache entries, session-related ephemeral state, distributed rate limiting and selected locks.
Background jobs
BullMQ over Redis. Dedicated worker process for email, search indexing, stock alerts, abandoned-cart reminders, exports, webhook retries and analytics aggregation.
Search
Meilisearch in Docker for typo-tolerant product search, facets, ranking and suggestions. Keep a database fallback for simple exact queries.
Object storage
S3-compatible adapter. Local MinIO in Docker; production-compatible with S3/R2 or equivalent.
Payments
Provider interface with a fully functional mock payment provider for local demo. Add Stripe test-mode adapter as the first real provider.
Email
Provider abstraction. Local Mailpit/MailHog for development; production adapter can be Resend/Postmark/SES.
Validation
Shared DTO/schema contracts using Zod where useful plus NestJS validation at API boundaries.
Testing
Vitest/Jest for unit and integration, Supertest for API integration, Playwright for browser E2E.
Observability
Structured logs, request IDs, health/readiness endpoints, metrics hooks and OpenTelemetry-ready instrumentation.
Architecture rules
Keep business rules in backend/domain services, not scattered through React components.
Use database transactions for order placement, payment recording, inventory reservations and refunds where consistency matters.
Use idempotency keys on sensitive write operations such as checkout, payment confirmation, refund and webhook processing.
Use an outbox/event pattern for post-transaction asynchronous work when a lost event would create incorrect behavior.
Never couple the storefront directly to Stripe, Redis, Meilisearch or object storage. Access these through service adapters.
Share only stable types/contracts across apps; do not share backend persistence models directly with the browser.
Prefer server rendering and cache-aware data access for SEO pages; hydrate only interactive islands.

API conventions
Base route /api/v1 with consistent resource naming and pagination metadata.
Use cursor pagination for large/high-churn resources when appropriate; page/limit is acceptable for stable admin tables.
Every error uses a stable machine-readable code, human-readable message, optional field errors, request ID and correct HTTP status.
OpenAPI docs must be generated and kept accurate enough to exercise core endpoints.
Input DTOs reject unknown/unsafe fields; outputs never leak password hashes, refresh-token hashes, private notes or provider secrets.
Write endpoints that can be retried safely should support Idempotency-Key. Webhook events must be de-duplicated by provider event ID.
Use optimistic concurrency or version checks where administrators can overwrite the same inventory/catalog records.

Core state machines
Order
draft → pending_payment → paid → processing → partially_fulfilled / fulfilled → completed. Alternate paths: payment_failed, cancelled, partially_refunded, refunded, return_requested/returned.
Payment
created → requires_action / processing → succeeded OR failed; succeeded → partially_refunded → refunded.
Fulfillment
unfulfilled → processing → shipped → delivered; support partial fulfillment and cancellation where valid.
Return
requested → approved/rejected → in_transit → received → inspected → refund_pending → refunded / exchanged / closed.
Inventory reservation
active → committed when order is finalized OR released on payment failure, cancellation or expiry.
Do not represent order lifecycle with one loosely controlled string. Enforce valid transitions in a domain service and test those transitions.

6. Search, caching, queues and realtime behavior
Search
Index searchable product title, description excerpt, SKU, brand, category, tags, option values, price, rating, popularity, stock and publication state.
Provide typo tolerance, prefix search, facets, sort options, synonyms-ready configuration and highlighted snippets where useful.
Reindex via queue on product/category/inventory changes. Include a CLI/admin command for full index rebuild.
Never expose unpublished or unauthorized products through the search index.
Caching
Use layered caching only for data that benefits from it: category navigation, product summaries, CMS content, selected analytics and rate-limit counters.
Invalidate or version cache entries when catalog/pricing/inventory data changes. Never cache user-private responses in shared cache keys.
Use Next.js cache controls intentionally on public pages; do not rely on accidental static rendering for data that changes frequently.
Queues and event-driven work
Email verification, receipts, shipping notifications, back-in-stock alerts, review requests and abandoned-cart messages.
Product search indexing, image processing hooks, CSV exports, analytics aggregation, stale reservation cleanup and webhook retry.
Every job has retry/backoff policy, bounded attempts, structured logging and dead/failure visibility in admin.
Realtime
Push admin notifications for new orders/failed payments and update customer order/fulfillment timelines through WebSocket or SSE where it improves UX.
Realtime is an enhancement, not the source of truth. Refreshing the page must always recover correct state from PostgreSQL.

9. UI system and interaction quality
Visual direction
Create a premium commerce identity with a neutral base, one restrained accent color, strong typography, generous but efficient spacing and editorial image composition.
Avoid generic “AI SaaS” gradients, excessive glassmorphism, neon glows, random floating blobs and dashboard styling on the consumer storefront.
Use product photography as the primary visual layer. Motion should be subtle: hover media transitions, drawer/sheet movement, cart feedback and route/loading transitions.

Use skeletons for loading, toast/inline feedback for operations, meaningful empty states and resilient error boundaries.
Component system
Build reusable primitives for buttons, links, inputs, selects, comboboxes, dialogs, sheets, popovers, tabs, accordion, table, pagination, badges, toasts, skeletons and form fields.

Admin components: data table, filters, bulk actions, stat card, chart wrapper, audit timeline, job status chip and destructive-action confirmation.

10. Security, privacy and reliability
Hash passwords with Argon2id. Apply password strength rules, rate limits and generic login/reset responses that do not leak account existence.
Use HTTP-only secure cookies where applicable; rotate refresh/session credentials and support logout-all/devices. Never store raw refresh tokens in the database.
Protect state-changing browser flows against CSRF as required by the chosen session strategy. Use SameSite, Origin/Referer validation and CSRF tokens where appropriate.
Use Helmet/security headers, CSP, strict input validation and output encoding. Sanitize any rich HTML allowed in CMS/product content.
Validate upload MIME/type/size; use randomized object keys; never trust user-supplied file paths.
Rate-limit login, password reset, coupon validation, checkout, review submission and public search endpoints with sensible policies.
Use role/permission guards on every admin API path; frontend route protection alone is insufficient.
Verify payment/webhook signatures, store provider event IDs, and process webhooks idempotently.
Protect inventory and coupon usage from race conditions using transactions, row-level locking/atomic updates or equivalent database-safe mechanisms.
Keep secrets only in environment variables/secret stores. Commit an .env.example with safe placeholders, never live credentials.
Audit financial, inventory, permission and destructive admin operations. Redact secrets and sensitive payment data from logs.
Add database backups/documented restore approach for production deployments and clear migration rollback/forward strategy.
11. Testing, performance and accessibility
Automated test expectations
Unit tests for pricing, promotions, taxes, inventory reservation, order transitions, refund math and permission checks.
Integration tests against a real test PostgreSQL instance for checkout, payment webhook idempotency, inventory consistency and returns.
API tests for auth lifecycle, catalog reads, cart mutation, checkout, admin permissions and error format.
Playwright E2E for guest purchase, authenticated purchase, coupon, failed payment/retry, order history, admin product edit and admin refund.
Test concurrency-sensitive scenarios: two checkouts competing for the last unit; duplicate payment webhook; repeated refund request; coupon limit reached.
Add smoke test script that seeds the app, starts services and verifies health + a storefront page + API endpoint.
Performance targets
Aim for Core Web Vitals in the good range on representative product/category pages under production build.
Optimize images with responsive sizes, stable aspect ratios and lazy loading below the fold.
Avoid client-fetch waterfalls for SEO-critical pages. Parallelize independent server fetches.
Use database indexes based on actual access patterns: slug, SKU, status, category relations, order/customer/date queries, coupon code, inventory variant/location, audit timestamps.
Profile N+1 query risks. Use select/projection to avoid returning oversized ORM objects.
Accessibility
Target WCAG 2.2 AA for navigation, forms, dialogs, drawers, tables, checkout and purchase flows.
Keyboard-only users must be able to search, filter, choose variants, add to cart and complete checkout.
Maintain visible focus, semantic headings, landmarks, accessible names, sufficient contrast, proper error association and reduced-motion support.

13. Definition of done
A first-time developer can clone, configure safe local env values, start Docker services, migrate/seed, and run the project without manually creating database rows.
Guest user can browse, search, filter, open a product, choose valid variant, add to cart and complete a mock-payment purchase.
Signed-in user can manage addresses, view orders, request a return, maintain wishlist and submit a review for an eligible purchase.
Admin can create/edit/publish a product, adjust inventory, manage a promotion, inspect an order, fulfill it, issue partial refund and review audit history.
Inventory cannot oversell in the tested last-unit race condition.
Duplicate checkout submission and duplicate webhook delivery do not create duplicate orders/payments.
Search index updates after catalog changes and can be fully rebuilt.
Emails appear in local mail viewer for verification/order/shipping/reset flows.
No major navigation item or visible CTA points to an unfinished screen.
No core chart, metric, product list or order list is a hard-coded frontend-only array once the backend is running.
Tests cover core business rules and critical E2E flows; lint/typecheck/build pass.
UI is responsive from small mobile through wide desktop and has polished loading, empty, error and success states.
Repository contains screenshots and a concise architecture explanation suitable for a technical portfolio.
Finish the end-to-end purchase and operations loops before adding decorative extras. A smaller number of deeply working modules is better than a large number of fake screens — but this specification expects all listed core modules to be implemented, not merely designed.

ADMIN & OPERATIONS

Admin modules: dashboard, products, variants, categories, collections, brands, inventory, warehouses, orders, customers, promotions/coupons, gift cards, loyalty, reviews/Q&A moderation, CMS/navigation/banners, roles/permissions, audit logs, jobs, webhooks, health and feature flags.
Large tables require server-side search/filter/sort/pagination, meaningful loading/empty/error states and CSV export. Catalog/inventory should support CSV import with validation report.
Every financial/destructive action uses confirmation and writes an audit record. Permission checks must be enforced by the API, never only by hidden buttons.
Admin analytics must query real seeded data and display revenue, net revenue, order count, AOV, refunds, cancellations, top products, low stock, customer growth, repeat customers and funnel-proxy metrics.
DATA MODEL
Create relational models for users, roles/permissions, sessions, addresses, products/variants/media/categories/brands/collections/options, warehouses/inventory/reservations/movements, carts/items, promotions/coupons/redemptions, gift cards/ledgers, loyalty/ledgers, checkouts, orders/items/addresses/history/notes, payments/attempts/refunds/webhooks, fulfillments/shipments, returns, reviews/Q&A, wishlists, recent views, back-in-stock subscriptions, CMS content, notifications/email deliveries, feature flags, audit logs, jobs and idempotency records.
Add appropriate unique constraints, foreign keys, indexes and money/quantity types. Avoid using JSON for core relational data just to save schema work.
AUTHENTICATION & SECURITY
Implement registration, login, logout, email verification, forgot/reset password, refresh/session rotation, logout-all/devices and account/session management. Use Argon2id for password hashing.
Use secure HTTP-only cookies where appropriate, rate limiting, CSRF defenses suitable to the auth strategy, strict CORS, security headers/CSP, DTO validation and sanitized rich content.
Never store raw refresh tokens. Never log secrets or payment-sensitive data. Validate upload type/size and randomize object keys.
Implement RBAC permission guards on backend routes. Add audit events for permissions, finance, inventory and destructive admin changes.
Provide safe .env.example files. No real credentials or hard-coded secrets.
SEARCH, CACHE, JOBS & EVENTS
Index product data into Meilisearch with typo tolerance, facets, ranking, availability filtering and suggestions. Queue incremental updates and support a full reindex command.
Use Redis selectively for cache, rate limits and short-lived coordination. Version/invalidate cache on catalog/pricing/inventory changes. Never cross-cache private user data.
Use BullMQ workers for email, search indexing, stock alerts, abandoned cart, review request, exports, analytics aggregation, stale reservation cleanup and webhook retry.
Each job has retry/backoff, bounded attempts, structured logs and operational visibility.
Use an outbox/event pattern for business events that must not be lost after a successful database transaction.
DUMMY DATA & DEMO EXPERIENCE
Seed at least 120 coherent products, 350 variants, 12–18 categories, 8–12 brands, 6 collections, two warehouses, 100 customers, 300 orders, 250 reviews, promotions, CMS content and analytics events.
Include examples of in-stock, low-stock, out-of-stock, sale, backorder, refunded, returned, failed payment and pending states so every screen can be demonstrated.
Provide deterministic demo accounts for customer, admin, operations and read-only/viewer roles. Print them after seed. Never enable demo credentials automatically in production.
Use local or permissively licensed placeholder assets; the store must not depend on a fragile external image host.
TESTING
Write unit tests for price math, promotions, tax, inventory reservations, state transitions, refund calculations and permissions.
Write integration tests against a real test PostgreSQL database for checkout, payment webhooks, inventory consistency, promotions and returns.
Use Supertest for API flows and Playwright for critical browser journeys: guest purchase, account purchase, coupon, failed payment retry, order history, admin product edit, inventory adjustment and refund.
Explicitly test last-unit concurrency, duplicate checkout submission, duplicate webhook and duplicate refund attempt.
CI must run lint, typecheck, unit/integration tests and production builds; include E2E where feasible.
PERFORMANCE, SEO & ACCESSIBILITY
Use Server Components by default for public pages and minimize client bundles. Avoid client-side waterfalls for SEO-critical content.
Implement metadata, canonical URLs, Open Graph, Product/Breadcrumb/Organization structured data, robots and dynamic sitemap.
Optimize images, fonts and route loading. Add database indexes based on access patterns and prevent N+1 queries.
Target WCAG 2.2 AA. All major journeys must work by keyboard, have visible focus, correct semantic landmarks, labeled controls, accessible dialogs/drawers and reduced-motion support.
LOCAL DEVELOPMENT & DEVOPS
Provide Docker Compose for PostgreSQL, Redis, Meilisearch, MinIO and Mailpit/MailHog. The web/api/worker can run through pnpm during development.
Required developer flow: pnpm install; docker compose up -d; migrate; seed; pnpm dev. Document all commands clearly.
Expose health/readiness endpoints and structured logs with request IDs. Make instrumentation OpenTelemetry-ready.
Add GitHub Actions for quality gates. Add Dockerfiles for api and worker. Document deployment options: Next.js web on Vercel or container; API/worker on a Node/container platform; managed PostgreSQL/Redis/search/object storage in production.
Never require a paid SaaS to demonstrate the project locally.
IMPLEMENTATION PROCESS
First inspect the repository and produce/update a short implementation plan. Then build vertically in working slices: infrastructure/schema → auth/catalog → cart/checkout/payment → orders/inventory → admin → engagement/advanced modules → testing/quality.
After each slice, run lint/typecheck/tests and fix regressions immediately. Keep the app runnable throughout.
Prefer working end-to-end behavior over broad scaffolding. However, do not leave any core requirement as a placeholder at final delivery.
When a requirement is ambiguous, choose a sensible production-style behavior and document the decision rather than stopping for trivial questions.
Keep code clean, modular and typed. Avoid giant services/components, copy-pasted business rules and unsafe any types.
At the end, run the production build, automated test suite and a smoke test. Verify the storefront and admin manually with representative flows.
